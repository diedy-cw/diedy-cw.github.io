1費用結構拆解：68% 跟流量走、32% 跟工作負載走

兩站月費 23,155 依成本驅動因素拆成兩類——前提「流量不變」，第一類原封不動搬到官網帳上；只有第二類理論上可省。

2「算力跟著流量搬家」——實測驗證

pod 處理流量會消耗算力，把流量倒進官網，official cluster 的消耗會漲。實測（2026-08-20 晚間尖峰 kubectl top 快照）確認了方向，也量出了尺度。

觀測項數值解讀
csr＋fc 全部 pod 實際 CPU 用量128m（0.13 核）其 2,030m requests 是 16 倍於實際用量的可用性底座（每 deployment 維持 2–3 副本，幾乎閒置）
兩站動態請求相對官網20.5M vs 224.6M（+9.1%）官網 app 承接後平均多 100–250m 實際負載
official cluster 尖峰行為1 → 2 台 e2-highcpu-8白天 1 台、晚間尖峰 autoscaler 開第 2 台、www pod 由 5 HPA 至 6——多的負載會反映在尖峰節點時數上
web cluster 節點使用率23–32%瓶頸在 requests 保留（排程密度），不在算力；縮節點的依據是釋出 2,030m 保留
正確的圖像：web cluster 釋出的是「2 核保留」不是「2 核算力」；真實算力（~0.13 核）搬到 official cluster 後，大多時間被既有 headroom 吸收，效果是尖峰第二台節點早一點開、晚一點關。若 web pool 沒有人工縮池，這個併站在 infra 帳上是純搬家、一毛不省還微增。

3風險與一次性成本

  1. 快取劣化風險：三站現況命中率（請求口徑）——csr 51%、www 44%、futurecity 21%。csr 頁面併入 www 的 app 後若沿用 www 的 cache 行為，csr 那部分回源流量會增加，CF 與 GCP Networking 同步微漲；futurecity 本來就低，無感。方向是漲不是跌，量級小但存在。
  2. 一次性搬遷工程不在月費內：CMS 內容遷移（csr-cms／csr-river-cms／futurecity-cms 三套併入 cw-cms）、全站 301 redirect、SEO 權重轉移與重收錄——工程與流量風險成本遠高於 infra 月省額。
  3. 假設：流量不變；www app 服務這些頁面的每請求算力效率不輸原 app；帳單口徑同三站報告（2026-07、匯率 32.58、含稅）。

4決策視角

如果動機是省 infra 費用，這個改動不值得——理想情況省 1.1%，還要付一次性搬遷工程。它真正的效益在營運面：少維護兩套站、三套 CMS、27 個測試環境 workload（合計 30+ deployment）。反過來，同樣的工程力氣投在 www 動態頁快取優化上，槓桿完全不同量級：官網 CF＋Networking 年費約 256 萬，而 www 命中率只有 44%——每拉高 10 個百分點都是以萬計的月省額。

5附註：本評估發現的報告精算點

  1. official cluster 權重低估：官網成本報告的 Compute 拆分以「official＝1 台 e2-highcpu-8」計權重，本次實測發現該 pool 尖峰會 autoscale 到 2 台——www 的 Compute 份額被低估，量級每月數百至低千元（取決於第二台的月均開機時數）。若官網報告要正式交付，建議以 7 月節點時數實際值修正（billing 明細或 Cloud Monitoring）。此點不影響本情境評估的結論。
